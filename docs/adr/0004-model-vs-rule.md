# 4. Model vs rule — argued from the table, not the vibe

Date: 2026-07-18
Status: Accepted

## Context

The thesis places anomaly detection in the value-adding tier of twin
services, and the honest question is whether a trained model earns its
keep over a three-line rule. `twin-services`' ADR-0002 already taught the
lesson that a benchmark can justify a decision by returning *nothing*
interesting; this ADR is where a model has to prove it beats an honest
baseline, per fault type, or admit it doesn't.

The comparison is real, not rhetorical: both detectors are fit on the same
normal-train windows, both take their threshold from held-out normal at the
same 1% false-positive budget, and both are scored on the same evaluation
set (68 held-out normal + 330 fault windows) by the same `detector` code
that `anomaly-svc` will serve. The rule was frozen before the forest
trained, so nothing was tuned to beat a moving target. Full table in
[EVALUATION.md](../EVALUATION.md); regenerate with notebooks 02 then 04.

## Decision

Serve the **Isolation Forest** (`isoforest-v1`) as `anomaly-svc`'s model,
and keep the **rule** (`rule-v1`) as the documented baseline — because the
table says neither dominates, and the forest wins exactly where it matters.

| recall by fault | rule | isoforest |
| --------------- | ---- | --------- |
| dropout         | 0.88 | 0.93      |
| encoder         | 0.47 | 0.20      |
| friction        | 0.00 | 0.61      |
| stuck           | 0.00 | 0.41      |
| **precision**   | 0.99 | 0.99      |
| **normal FPR**  | 0.01 | 0.01      |

**The rule wins on encoder, and it is not close** (0.47 vs 0.20). Encoder
noise drives `pos_std` far outside a tight normal band, and a per-feature
envelope catches exactly that — a decisive move in one feature. Say so
plainly: on this fault, the model is worse than three lines of code.

**The forest wins decisively on friction and stuck** (0.61 and 0.41 vs
0.00). These faults only *attenuate* velocity, and normal velocity RMS
already varies widely because the arm is running a sine — so a stuck joint
sits at the low edge of an already-wide band, never decisively out of it
(69% of stuck windows fall below the normal 1st percentile, but only just).
The rule, thresholded at 1% FPR, can't separate that from normal variation.
The forest can, because "this joint is quiet while the pattern says it
should be moving" is a *multivariate* statement no single-feature band
makes. Friction and stuck are the mechanically meaningful faults — the ones
a maintenance twin exists to catch — so the forest earns its place on the
faults that matter.

**They tie on dropout** (0.88 vs 0.93): `n_samples` collapses, both notice.

Precision (0.99) and normal FPR (0.01) are identical by construction — the
shared threshold policy fixes the false-alarm budget, which is what makes
recall the fair axis of comparison.

## Consequences

- `anomaly-svc` loads `isoforest-v1`. Its manifest carries the threshold and
  the `features/` version; the rule ships alongside as `rule-v1` for anyone
  who wants a near-free detector for the loud faults (dropout, encoder).
- The finding is nuanced on purpose and must not be rounded to "the model
  won." A reader who only needs dropout/encoder detection should use the
  rule; the model is justified specifically by friction and stuck.
- **Honest bounds.** These are synthetic signal-path faults (ADR-0002): the
  numbers say what is learnable from *kinematics* at these severities, not
  what a real robot's effort/current signatures would yield. Encoder recall
  is modest for both (0.47 / 0.20) — subtle position noise is genuinely
  hard from position statistics alone. Do not quote these as the ceiling of
  either method; quote them as this corpus's result.
- The corpus is regenerated by `just collect && just dataset` over one
  operating span; each artefact's manifest pins the exact dataset by sha256,
  so a model can always be traced to the data that made it.

## What the LSTM autoencoder would add — deferred

The ROADMAP names the LSTM autoencoder the first thing to cut if Phase 3
slips, and it is deferred (notebook 03 documents the plan). The open
question it would answer: friction and stuck are *temporal* faults — a
frozen or lagging joint is anomalous in how the signal evolves, not just in
a window's summary statistics. An autoencoder over the raw window sequence
might beat the forest there, or might not clear it; either way its column
slots into this same table under the same threshold policy, and the
`detector.Scorer` protocol already accommodates it. Until it exists, the
comparison stands at rule vs forest, and the decision above holds.
